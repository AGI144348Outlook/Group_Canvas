# Private derived tower filters

Authorized by Timothy: two tower instantiations over the existing private R2 cabinet. Confirmed names: Julian, Nexus, Concord, Zenith. No new buckets; no changes to original archives.

`filter-towers.yml` executes on this module's changes or manual dispatch. The runner obtains the existing storage credential from repository secrets. Source text stays in private R2 and temporary private Actions-runner files, deleted in `finally`; no source-text artifacts or logs are published. Only aggregate counts appear in logs. This is a deterministic batch scan, not an AI service or trained model.

The resulting named cabinet collections are persistent tower instances, each with versioned manifests and per-source JSON records. My prompts includes every recorded user-role message, including alternate branches, quotations, and messages without text. This does not establish the authorship of quoted text or approve any clone profile. Character mentions scans text across all roles for case-insensitive complete-name matches using Unicode letter/number/underscore boundaries. No aliases, pronouns, semantic attribution, speaker identification, or character memories are inferred. Common words Nexus/Concord/Zenith may produce false positives. Both views may legitimately reference the same message.

Every derived message retains source file ID, full source SHA-256, conversation byte range and hash, conversation ID, ordinal, mapping node ID, parent, children, selected endpoint, recorded role, message ID, and nontext count. Nontext attachments remain only in the source. Mapping iteration is not claimed to be chronological. Missing branches are not invented. Identical entire source files are recognized by SHA-256; occurrences across differing sources remain distinct.

Completed source files only. Unfinished entries are listed in manifests. No automatic upload-completion trigger exists yet: rerun the workflow to include newly completed files. Failure prevents publication of a new final manifest for the affected scan; already written per-source outputs may remain in the cabinet. Old successful manifests remain accessible. Content-addressed output IDs make reruns safe. Existing objects are not erased. Private download tickets are never printed.

Limits: 5,000 cabinet metadata rows, 512 MiB/source download, 32 MiB/conversation framing, 512 MiB aggregate per-source derived JSON string budget; processing is one source/conversation at a time but output arrays accumulate for a source. This is a bounded prototype, not a production streaming index or subscription query system. Runner network interruptions require a rerun; previous uploads are reused by identity. The phone viewer loads individual derived parts up to 32 MiB and renders 20 messages at a time. Larger outputs can be downloaded through the cabinet. New files are independent derived copies linked by provenance, not full original archive duplication.

Viewer: `/filter-towers.html`, operator code held in page memory only. The reserved hierarchy is Datasets → Registries → Matrices → Indices → Codices → Algorithms → Logics. Datasets displays source references; Registries browses filtered occurrence records. Higher floors are explicitly unpopulated. This does not implement personality identity, a matrix reasoner, executable governance, or GraphQL.

Validation: `node tools/tower-filters/filter.test.mjs` (3 tests), `node tools/tower-filters/run.test.mjs` (mocked private storage end-to-end including checksum verification, duplicate detection, pending exclusion and original preservation). Live results must be checked independently in Actions. No Android browser session has been tested here.
