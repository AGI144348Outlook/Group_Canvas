### Finding: Claude's client collapses the `oneOf` widget schema

In the Claude chat, the `widget_create` tool was presented with **only the first
alternative** (`kind: const "note"`, note spec) and `additionalProperties: true`. A quiz
sent anyway was accepted by the server, but an assistant reading the schema at face value
would think only notes are possible. This confirms the earlier `oneOf` → `anyOf` concern
with a real host.

Proposed fix (not done yet): replace the top-level `oneOf` with one flat object schema —
`kind` as an `enum` of all widget kinds, `spec` as `anyOf` of the per-kind specs (the
`widget_update` tool already uses `anyOf` for `spec` and rendered correctly), and keep
service-side validation as the authority. Please confirm or propose an alternative;
`src/widgets/schema.js` is your module.

### Finding: duplicate connector seats

while setting up. Only one is in use, but all four links are live and identical in the

owner can remove extras, and reject a second link with the same name unless confirmed.

## 4. Proposal A — keep rooms reachable (storage)

**Problem.** Room data is durable (Durable Object SQLite), but the client keeps its
credential only in `sessionStorage` (`gc-room`), and tokens expire after 24 h. Closing the
tab or waiting a day leaves the owner unable to re-enter their own room. No accounts
exist to re-issue access. There is also no service worker or offline shell.

**Proposed (prototype step until accounts):**

1. **"My rooms" in IndexedDB.** Store `{room, title, role, token, updatedAt}` for rooms
   created or joined; list them on the welcome screen. Data stays in the Durable Object;
   IndexedDB only holds pointers and credentials.
2. **Refresh on open.** If a stored token is still valid, call `/refresh` immediately and
   on an interval, so the 24 h limit only bites after a full day away.
3. **Owner recovery key.** At room creation, issue a second long-lived secret (same
   pattern as connector links: 256-bit key, only its hash in state). Store it in IndexedDB
   and show it once for the owner to save. `POST /recover {key}` returns a fresh owner
   token on any device. Rotation and revocation by the owner. Accounts later replace it.
4. **Service worker** caching the static shell (`index.html`, `app.js`, `style.css`,
   `python-worker.js`) for instant load and home-screen install. Never cache `/api/*`.

**Questions for Codex:** (a) any objection to a long-lived owner credential before
accounts, versus contract §2.2's ≤ 24 h tokens? It would be a separate credential type
that only mints normal short tokens. (b) Should the recovery key bump the owner's epoch
on use (invalidating other owner sessions) or not? (c) Anything in `app.js` session
handling this should hook into rather than replace?

## 5. Proposal B — comic/manga widget + server-side Claude seat

**Timothy's request.** When he chats **in the canvas chat box**, an AI answers in text
**and** posts a comic/manga strip widget illustrating the reply, whenever the AI judges
it useful, and always when asked.

**Widget-type rule (explained to Timothy):** any widget type is possible, but each needs
a renderer in the app; AIs only supply validated data, never executable code. So `comic`
is a new kind.

**Proposed `comic` spec (draft):**

```js
{
  readingOrder: 'ltr' | 'rtl',          // western or manga
  style: 'manga' | 'western' | 'chibi',
  panels: [ /* 1–6 */ {
    layout: 'full' | 'half' | 'third',  // panel width in its row
    background: 'plain' | 'speedlines' | 'sparkles' | 'gloom' | 'sky' | 'room',
    caption?: string,                   // ≤ 200
    characters: [ /* ≤ 3 */ {
      name: string,                     // ≤ 40
      glyph: string,                    // ≤ 4, e.g. 'ג', '✦', 'א'
      expression: 'neutral'|'happy'|'surprised'|'thinking'|'sad'|'determined',
      position: 'left' | 'center' | 'right',
    }],
    bubbles: [ /* ≤ 3 */ {
      type: 'speech' | 'thought' | 'shout' | 'whisper',
      from: number,                     // index into characters
      text: string,                     // ≤ 160
    }],
    sfx?: string,                       // ≤ 20, e.g. 'BAM', 'ドン'
  }],
}
```

Rendered client-side as SVG with `textContent` only. Size caps keep it small.

**Server-side Claude seat.** Uses the existing Anthropic adapter (`provider: 'anthropic'`).
Needs `ANTHROPIC_API_KEY`, `ALLOW_PAID_PROVIDERS=true`, and a ≥ 24-char
`CREATE_ROOM_KEY` (already set). Billed per use via the API, separate from Timothy's
Claude plan. Capped by the room allowance (`DAILY_TURNS=30`). The offline demo seat can
emit a fixed sample comic for key-free testing.

**Questions for Codex:** (a) `comic` fits `src/widgets/schema.js` + a renderer in `app.js`.
Who builds which half? Proposed: Codex owns schema/validation and the renderer; Claude
owns the provider prompt/tool changes so seats emit comics, plus the demo sample.
(b) Should AI turns currently limited to the main thread (`checkMain`) stay that way for
this feature? (c) Any objection to the draft spec fields or limits?
